# 성능 측정

주문 API에 부하를 걸어 처리량과 지연을 재고, 끝난 뒤에도 장부가 맞는지 확인한다.

## 도구

`LoadTest`(`backend/src/test/java/com/fanchart/load`)는 일반 테스트에서 빠지고 `loadTest` 작업으로만 돈다.

```bash
cd backend
docker compose up -d
SPRING_DATASOURCE_URL='jdbc:mysql://localhost:3306/teamtrading?useLocalSessionState=true&rewriteBatchedStatements=true&cachePrepStmts=true&useServerPrepStmts=true&prepStmtCacheSize=250' \
  ./gradlew loadTest -Pload.users=50 -Pload.seconds=20 -Pload.teams=3
cat build/reports/load/summary.txt
```

동작 방식:

- 사용자마다 개발용 로그인 세션을 하나 두고, 구단마다 200주를 지급한다.
- 정해진 시간 동안 기준가 ±3호가 지정가 주문(1~3주)을 쉬지 않고 보낸다. 열 번에 한 번은 대기 주문을 취소한다.
- 끝나면 다음을 확인한다. 하나라도 어긋나면 실패다.
  - 5xx·연결 오류 0건
  - `PENDING` 주문 0건
  - 묶인 포인트 합 = 대기 매수 주문 예치 합
  - 호가가 교차하지 않음
  - 원장 대사 일치
- 지연과 처리량은 실행 환경에 따라 달라서 기준을 두지 않고 기록만 한다.

CI의 MySQL 작업은 20명 × 15초로 매번 돌리고, 결과를 작업 요약에 남긴다.

## 봇 1,000개 화면 부하 (2026-11-11)

`LoadTest`는 주문만 보낸다. 실제 사용자는 화면을 켜 두고 3초마다 조회 10건을 보내고, 가끔 주문한다. 이 패턴은 봇 실행기(`tools/bots/bots.mjs`, [bots.md](bots.md))로 잰다. 집 PC에서는 운영과 분리한 측정 스택(`deploy/compose.load.yml`)에 붙인다.

환경: 4 vCPU 컨테이너 하나에 서버, MySQL 8.4, 봇 실행기를 함께 돌렸다. nginx 없이 서버에 바로 붙었고 구단은 18개다. 봇 하나가 초당 약 3.7건을 보낸다. 트러블슈팅 47 수정 후 값이다.

| 봇 | 조회 처리량 | 조회 p50 | 조회 p95 | 주문 처리량 | 주문 p95 | 오류 |
| --- | --- | --- | --- | --- | --- | --- |
| 20 | 73건/초 | 7ms | 12ms | 1.4건/초 | 26ms | 0 |
| 100 | 368건/초 | 4ms | 10ms | 3건/초 | 28ms | 0 |
| 300 | 1,100건/초 | 6ms | 19ms | 9.5건/초 | 43ms | 0 |
| 800 | 1,650~1,940건/초 | 1.4~1.9초 | 2.1~2.3초 | 18~21건/초 | 2.1초 | 0 |

20·100·300개는 수정 전 실행 값이다(수정 전에도 이 구간에서는 막히지 않았다). 300개까지는 여유가 있고 600개 근처에서 CPU가 꽉 차 지연이 초 단위가 된다. 봇 실행기가 CPU 한 개를 쓰므로 다른 기기로 빼면 한계는 더 올라간다.

## 새로 고침 요청 묶기 전후 (2026-11-12)

화면이 3초마다 보내던 조회 11건을 `/api/refresh` 한 건으로 묶은 전후다([ADR 0041](adr/0041-one-request-per-refresh.md), 트러블슈팅 49). 환경: 4 vCPU 컨테이너 하나에 서버, MySQL 8.4, 봇 실행기. 구단 140개, nginx 없이 서버에 바로 붙었다. CPU는 봇이 다 붙은 뒤 50초 동안 프로세스가 쓴 CPU 시간이고, 100%가 CPU 한 개다.

| 봇 | 방식 | 초당 요청 | 서버 CPU | MySQL CPU | p95 |
| --- | --- | --- | --- | --- | --- |
| 300 | 11건 | 1,100 | 73% | 38% | 10~17ms(요청 한 건) |
| 300 | 1건 | 100 | 42% | 32% | 13~15ms(새로 고침 한 번) |
| 600 | 11건 | 2,140~2,200 | 113% | 64% | 67~233ms(요청 한 건) |
| 600 | 1건 | 200 | 60% | 59% | 16~20ms(새로 고침 한 번) |
| 1,000 | 1건 | 330 | 84% | 86% | 43~54ms(새로 고침 한 번) |

보안 필터 관측만 끈 경우(11건)는 봇 300개에서 서버 CPU 56%, MySQL 33%였고, 묶은 뒤에 함께 끄면 43%로 묶기만 한 것과 같았다. 봇 1,000개는 실행마다 차이가 커서, 관측도 끄고 잰 다른 실행에서는 서버 102%, MySQL 98%, p95 118~276ms였다. 모든 실행에서 5xx와 연결 오류는 0건이었다.

## 집 PC 측정 (2026-11-12)

환경: 서버는 집 PC(i3-8100 4코어 4스레드, 메모리 7.7GB)의 측정 스택(`compose.load.yml`, 운영 백업 복사, 구단 140개, nginx 경유)이다. 같은 PC에 실서버 스택도 떠 있었다. 봇 실행기는 다른 PC에서 Tailscale(왕복 16ms)로 붙었고, 응답 시간에는 이 왕복이 들어 있다. 봇 1,000개를 5분에 걸쳐 늘렸다.

280개를 넘으면 연결 오류가 대부분이라 처리량 숫자에 실패가 섞인다. 이때 CPU 87~100%, 메모리 94%, 디스크 C: 73~82%, 이더넷 보내기 7~11Mbps였다. 막힌 곳은 네트워크가 아니라 PC의 CPU·메모리다(트러블슈팅 48). 이 PC의 한계는 봇 200개 안팎이다.

## 결과 (2026-11-02)

환경: 4 vCPU 컨테이너 하나에서 부하 클라이언트, 서버, MySQL 8.4(docker, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`)를 함께 돌렸다. 측정 중 load average가 10까지 올라 CPU가 포화됐다. 그래서 절대값은 하한으로 보고, 같은 환경에서 나란히 비교한 값만 의미가 있다.

## 병목

JFR로 보면 50명 부하에서 요청 스레드 대기 시간의 대부분이 종목 락(`TradingService.place`의 `market.lock.lock()`) 대기다. CPU 실행 샘플은 적었다. 종목 락을 잡고 있는 동안 걸린 시간을 임시 계측으로 나누면 다음과 같다(50명, 3구단, 주문당 평균).

| 구간 | 드라이버 기본값 | 드라이버 설정 후 |
| --- | --- | --- |
| 검증·멱등키 조회 | 1.2ms | 1.0ms |
| 접수 트랜잭션 (주문 저장, 예치) | 10.5ms | 8.5ms |
| 매칭 (메모리) | 0.1ms 미만 | 0.1ms 미만 |
| 정산 트랜잭션 (체결, 잔고, 원장) | 10.4ms | 8.6ms |
| 시세 발행 | 0.2ms | 0.2ms |
| 합계 | 22.5ms | 18.5ms |

한 구단의 주문은 이 구간을 하나씩 지나가므로 구단당 처리량의 상한은 약 1 / 18.5ms ≈ 54 주문/초다. 락 안 시간의 90% 이상이 DB 트랜잭션 두 번이다. `performance_schema`로 보면 주문 하나에 문장이 약 20개 나가고, 그중 COMMIT 두 번이 평균 2.4ms씩으로 가장 크다.

## 적용한 개선

DB URL에 MySQL 드라이버 설정을 넣었다. 동작과 트랜잭션 경계는 바뀌지 않는다.

- `useLocalSessionState=true`: 트랜잭션마다 나가던 `SET autocommit`, `SELECT @@session.transaction_read_only` 왕복을 줄인다.
- `rewriteBatchedStatements=true`: 원장 분개(주문당 약 5행)를 한 번의 다중 행 INSERT로 보낸다.
- `cachePrepStmts`, `useServerPrepStmts`, `prepStmtCacheSize=250`: 서버 측 준비문을 연결마다 캐시한다.

## 다음 후보

효과가 크지만 설계를 바꾸는 일이라 측정 근거만 남겨 둔다.

1. **주문당 트랜잭션 하나로 합치기.** 지금은 접수와 정산을 따로 커밋한다(ADR 0003). 합치면 락 안 커밋이 절반이 된다. 대신 정산 실패 시 접수 기록도 함께 사라지므로 실패 처리와 기동 복구를 다시 설계해야 한다.
2. **구단별 묶음 커밋.** 락 안에서 여러 주문을 매칭하고 한 트랜잭션으로 정산한다. 커밋 수가 묶음 크기만큼 줄지만, 응답은 묶음 커밋 뒤에 보내야 한다.
3. **실제 서버에서 다시 재기.** 부하 클라이언트를 다른 장비로 빼고, 배포할 DB(예: RDS gp3)에서 커밋 지연을 따로 잰다.
