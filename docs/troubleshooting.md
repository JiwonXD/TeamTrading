# 트러블슈팅 기록

개발하면서 실제로 부딪힌 버그, 정합성 문제, 설계 고민을 모은다. 항목마다 문제 → 원인 → 해결 → 결과 → 배운 점 순서로 적고 관련 PR을 단다.

- **구분.** `버그`는 실제로 잘못 동작한 것을 찾아 고친 일이다. `설계`는 잘못될 수 있는 경로를 먼저 찾아 구조로 막은 일이다. 둘을 섞어 쓰지 않는다.
- **수치.** 테스트·측정에서 나온 값만 적는다. 측정 환경이 결과에 영향을 주면 함께 적는다.
- **누적.** 새 문제를 해결하면 맨 아래 템플릿으로 항목을 더하고 색인 표에도 한 줄 넣는다.

## 1. 응답을 못 받은 주문 재시도가 두 번 체결될 수 있음

- 구분: 설계 / 주제: 멱등성
- 관련: [#2](https://github.com/JiwonXD/TeamTrading/pull/2), [#3](https://github.com/JiwonXD/TeamTrading/pull/3), [#7](https://github.com/JiwonXD/TeamTrading/pull/7), [#17](https://github.com/JiwonXD/TeamTrading/pull/17), [ADR 0004](adr/0004-client-order-id.md)

**문제.** 주문을 보낸 뒤 네트워크가 끊기면 클라이언트는 주문이 들어갔는지 모른다. 다시 보내면 같은 주문이 두 번 체결될 수 있다. 증권 주문에서 가장 피해야 할 오류다.

**원인.** 서버가 "같은 의도의 재요청"과 "새 주문"을 구별할 근거가 요청에 없었다. 요청 내용 해시로 판단하면 같은 가격·수량으로 일부러 두 번 낸 주문을 구별하지 못한다.

**해결.**
- 클라이언트가 주문마다 `clientOrderId`를 만들어 보낸다(FIX의 ClOrdID, Stripe 멱등키와 같은 방식).
- 처음에는 메모리 맵으로 구현했다가, DB를 붙이면서 `UNIQUE (account_id, client_order_id)` 제약으로 옮겼다. 재시작해도 잊지 않는다.
- 같은 번호의 재요청은 저장된 접수 결과를 그대로 돌려준다. 동시에 들어온 재시도는 첫 요청이 끝날 때까지 기다린다.
- 같은 번호로 내용이 다른 주문은 409로 거절한다. 잔고 부족처럼 접수 전에 거절된 주문은 저장하지 않아, 고쳐서 같은 번호로 다시 보낼 수 있다.
- 화면은 번호를 먼저 정해 보내고, 응답을 못 받으면 같은 번호로 한 번 재전송한다.

**결과.**
- 8스레드가 같은 번호로 동시에 재시도해도 주문은 1건만 생긴다.
- `kill -9` 장애 테스트(항목 2)에서 주문 1,736건 중 응답을 못 받은 28건을 같은 번호로 재시도했고, 5xx 없이 한 번호가 두 주문으로 갈라지는 일이 없었다.

**배운 점.** 멱등성은 "중복 요청을 막는 기능"이 아니라 "실패한 요청을 안전하게 다시 보낼 수 있게 하는 계약"이다. 그래서 거절된 요청은 번호를 소모하지 않게 하는 것까지 설계에 들어가야 했다.

## 2. 메모리 매칭과 DB 잔고 사이에서 서버가 죽는 경우

- 구분: 설계 / 주제: 정합성, 장애 복구, 교착 회피
- 관련: [#3](https://github.com/JiwonXD/TeamTrading/pull/3), [#17](https://github.com/JiwonXD/TeamTrading/pull/17), [ADR 0002](adr/0002-per-team-lock.md), [ADR 0003](adr/0003-two-transactions-per-order.md)

**문제.** 매칭은 속도를 위해 메모리 호가창에서 하고, 잔고는 MySQL에 있다. 매칭 결과와 DB가 어긋나거나, 처리 도중 서버가 죽으면 포인트가 사라지거나 묶인 채 남을 수 있다.

**원인.** 한 주문의 처리가 "잔고 확인 → 매칭 → 체결 반영" 여러 단계에 걸쳐 있다.
- 체결 한 건마다 트랜잭션을 나누면 한 주문이 여러 건에 체결될 때 중간 상태가 DB에 남는다.
- 접수와 정산을 한 트랜잭션으로 묶으면 잔고 확인 전에 메모리 매칭이 먼저 일어나 호가창을 되돌리기 어렵다.

**해결.** 주문 하나를 트랜잭션 두 개로 나누고, 각 실패 경로에 복구 절차를 정했다.
1. 접수 트랜잭션: 포인트·주식을 조건부 UPDATE(`WHERE available >= ?`)로 묶고 주문을 `PENDING`으로 저장한다. 칼럼마다 `CHECK (>= 0)`을 둬 음수 잔고는 DB가 거부한다.
2. 메모리 매칭(종목별 공정 락 안).
3. 정산 트랜잭션: 체결, 상대 주문 잔량, 차액 환불, 주문 상태를 한 번에 반영한다.

- 정산이 실패하면 그 주문을 취소·예치 해제하고 호가창을 DB에서 다시 쌓는다. 그것도 실패하면 그 종목 거래만 멈춘다.
- 재시작 때 `PENDING`으로 남은 주문(두 트랜잭션 사이에 죽은 경우)은 취소하고, `OPEN` 주문을 접수 순으로 읽어 호가창을 복구한다.
- 서로 다른 종목의 정산이 같은 계정 행을 엇갈려 잠그면 InnoDB 교착이 날 수 있으므로, 정산 때 계정 행을 항상 id 순서로 갱신한다.

**결과.**
- MySQL 8.4에서 8스레드 동시 거래: 주문 1,618건, 체결 1,045건, 포인트 총량 보존, 교착 0건.
- `tools/chaos/run.sh`로 주문을 받는 중 서버를 `kill -9`로 죽이고 재시작하기를 3회 반복했다. 매 회차 확인 항목은 응답받은 주문 보존, 재시도 멱등성, `PENDING` 0건, 묶인 포인트 = 대기 매수 예치 + 청약 증거금, 원장 대사 일치였고 모두 통과했다. 한 회차는 죽는 순간 `PENDING` 주문이 2건 있었고, 재시작 때 취소·예치 해제됐다.
- 이 장애 테스트는 CI에서 매번 돈다.

**배운 점.** 장애 복구는 "죽지 않게"가 아니라 "어디서 죽어도 돌아올 상태가 정해져 있게" 설계하는 일이다. 중간 상태(`PENDING`)를 명시적으로 두니 복구 규칙이 한 줄로 정리됐고, 실제로 죽여 보는 테스트로 그 규칙을 검증할 수 있었다.

## 3. 잔고가 맞는지 증명할 방법이 없음

- 구분: 설계 / 주제: 정합성, 감사
- 관련: [#4](https://github.com/JiwonXD/TeamTrading/pull/4), [#8](https://github.com/JiwonXD/TeamTrading/pull/8), [#12](https://github.com/JiwonXD/TeamTrading/pull/12), [#15](https://github.com/JiwonXD/TeamTrading/pull/15), [ADR 0005](adr/0005-double-entry-ledger.md), [ADR 0015](adr/0015-observability.md)

**문제.** 잔고 테이블은 현재 값만 갖는다. 버그나 직접 수정으로 값이 틀어져도 알 방법이 없고, 언제 어디서 틀어졌는지도 추적할 수 없다.

**원인.** 잔고 변경의 근거(누가, 왜, 얼마)가 따로 남지 않았다.

**해결.**
- 모든 포인트·주식 이동(개설, 지급, 예치, 체결, 해제)을 잔고 갱신과 같은 트랜잭션에서 복식부기 전표로 남긴다. 자산별 분개 합이 0이어야 전표가 생성되고, 새로 생기는 몫은 발행처(`SYSTEM`) 칸에서 나온다.
- 대사: 원장을 계정·자산·칸별로 합산해 잔고 테이블과 비교하고, 합이 0이 아닌 전표를 찾는다. 한 읽기 트랜잭션(REPEATABLE READ)에서 읽어 같은 시점끼리 비교한다.
- 이후 기능도 같은 장부에 맞췄다. 포인트 발행은 `PointIssuer` 한 곳에서만 하고 발행 기록 합 = 원장 발행 총량을 대사에 넣었다(#8). 공모 대금 소각 합 = 배정 기록도 대사한다(#12).
- 5분마다 대사를 자동으로 돌려 Prometheus 지표(`fanchart_reconciliation_balanced`)로 내보내고, 어긋나면 경보를 울린다(#15).

**결과.**
- 실행 중인 서버에서 잔고를 7P 바꾸자 대사 API가 그 칸을 불일치로 보고했다. 전표를 직접 고친 경우도 찾아냈다.
- MySQL 동시성 테스트: 체결 1,056건, 전표 3,051장 후 대사 일치.
- 부하 테스트, 장애 테스트, 이후 모든 기능 테스트가 "끝나고 대사 일치"를 통과 조건으로 쓴다.

**배운 점.** "버그가 없다"는 주장보다 "틀어지면 바로 안다"는 장치가 더 믿을 만하다. 원장을 먼저 깔아 두니 이후 배당·공모·탈퇴 같은 기능마다 정합성을 같은 방식으로 검증할 수 있었다.

## 4. 이상거래 탐지 기록이 재시작하면 사라짐

- 구분: 버그 / 주제: 정합성, 감시
- 관련: [#24](https://github.com/JiwonXD/TeamTrading/pull/24), [ADR 0021](adr/0021-persisted-fds-alerts.md)

**문제.** 이상거래 탐지(가격 괴리 10%, 10분 안 같은 상대와 5회) 기록이 메모리에 최근 200건만 있었다. 재시작하면 기록이 사라지고, 리더보드에서 빼야 할 몰아주기 계정이 다시 순위에 올라왔다.

**원인.** 두 가지였다.
- 저장 위치가 메모리였다.
- 탐지가 체결 정산이 커밋된 **뒤에** 돌았다. 그래서 그 사이 서버가 죽으면 체결은 남고 탐지 기록은 없는 상태가 될 수 있었다. 단순히 DB에 저장하도록 바꾸는 것만으로는 이 틈이 남는다.

**해결.**
- `fds_alerts` 테이블을 두고 체결 id를 외래키로 건다.
- 매칭 결과가 나오면 정산 **전에** 탐지를 돌리고(시세는 아직 바꾸지 않고 이번 체결을 차례로 더해 가며 본다), 결과를 정산과 같은 트랜잭션에 저장한다.
- 탐지 기록 저장이 실패하면 체결도 롤백하고 주문을 취소한다. 기존 정산 실패 경로를 그대로 쓴다.
- 감시 화면과 리더보드 자격을 모두 DB에서 읽는다.
- 재기동 때 체결 내역으로 다시 탐지하는 방법은 버렸다. 탐지 규칙이 바뀌면 과거 기록이 달라져 감사에 맞지 않는다.

**결과.** 재기동 뒤에도 두 종류 기록이 그대로 남고, 각 기록이 가리키는 체결이 실제로 있으며, 탐지 기록 저장이 실패하면 체결이 남지 않고 포인트와 대사가 그대로인 것을 테스트로 확인했다.

**배운 점.** "감시 기록 없는 체결"을 허용할지는 기술 문제가 아니라 정책 문제다. 저장 실패 시 거래를 막는 쪽을 택했고, 그 근거를 ADR에 남겼다.

## 5. 공개 응답에 나간 계정 id로 남의 주문을 낼 수 있었음

- 구분: 버그 / 주제: 보안
- 관련: [#7](https://github.com/JiwonXD/TeamTrading/pull/7), [#9](https://github.com/JiwonXD/TeamTrading/pull/9), [ADR 0009](adr/0009-session-login.md)

**문제.** 화면을 서버에 연결하면서 응답을 살펴보니, 수익률 랭킹과 감시 기록에 계정 id가 그대로 나가고 있었다.

**원인.** 그 시점에는 `X-Account-Id` 헤더가 인증 수단이었다. 계정 id를 아는 것이 곧 그 계정으로 주문할 권한이라, 랭킹을 본 누구나 다른 사람 계정으로 주문할 수 있었다.

**해결.**
- 바로 막기(#7): 랭킹은 계정 id 대신 요청자 본인 행에만 `me: true`를 붙이고, 감시 기록은 닉네임으로 바꿨다.
- 근본 해결(#9): 헤더 인증과 누구나 계정을 만들던 `POST /api/accounts`를 없애고 카카오·네이버·구글 로그인과 세션 쿠키로 바꿨다. 로그인 때 세션 id를 교체하고, 상태를 바꾸는 요청에 CSRF 토큰을 요구한다.

**결과.** 이후 공개 API 테스트마다 "응답에 계정 id 없음"을 검사 항목으로 넣었다. CSRF 없는 주문은 403이다.

**배운 점.** 식별자와 인증 수단이 같으면 식별자를 노출하는 모든 화면이 보안 구멍이 된다. 임시 인증을 쓰더라도 그 값이 어디로 나가는지 함께 봐야 했다.

## 6. 한도 초과 예외 하나가 바깥 트랜잭션 전체를 롤백시킴

- 구분: 버그 / 주제: 트랜잭션
- 관련: [#14](https://github.com/JiwonXD/TeamTrading/pull/14)

**문제.** 게시글 보상을 지급하는 트랜잭션 안에서 포인트 발행 하루 한도를 넘으면, 보상만 건너뛰는 게 아니라 글 상태 갱신을 포함한 바깥 트랜잭션 전체가 롤백됐다.

**원인.** `PointIssuer.grant`가 한도 초과를 예외로 알렸다. Spring에서 트랜잭션 경계 안의 메서드가 런타임 예외를 던지면, 바깥에서 그 예외를 잡아도 트랜잭션이 이미 rollback-only로 표시돼 커밋할 수 없다.

**해결.** 한도 초과를 예외 대신 빈 값으로 돌려주는 `grantWithinLimit`를 추가하고, 기존 `grant`는 이를 감싸게 했다. 한도 초과는 "정상적인 결과 중 하나"로 다루고, 그 글의 보상 상태는 `NONE`으로 둔다.

**결과.** 하루 3번 한도를 넘은 글은 보상 없이 처리되고, 다른 갱신은 정상 커밋된다. 이후 광고 보상 콜백(#20)도 같은 메서드로 한도 초과를 LIMIT 상태로 끝낸다.

**배운 점.** 예외는 "처리할 수 없는 상황"에만 쓴다. 업무 규칙상 예상되는 결과(한도 초과)를 예외로 표현하면 트랜잭션 전파 규칙과 엮여 엉뚱한 곳까지 실패한다.

## 7. 주문 처리량 병목 측정과 개선

- 구분: 성능 / 주제: 성능, 동시성
- 관련: [#16](https://github.com/JiwonXD/TeamTrading/pull/16), [docs/performance.md](performance.md)

**문제.** 동시 사용자가 늘면 주문 지연이 얼마나 늘고, 어디가 병목인지 몰랐다. 또 부하 중에도 장부가 맞는지 확인한 적이 없었다.

**원인 분석.**
- 사용자마다 로그인 세션을 두고 기준가 근처 지정가 주문·취소를 쉬지 않고 보내는 `LoadTest`를 만들었다. 끝나면 5xx 0건, `PENDING` 0건, 묶인 포인트 = 대기 매수 예치 합, 호가 비교차, 대사 일치를 모두 확인한다.
- JFR로 보니 50명 부하에서 요청 스레드 대기의 대부분이 종목 락 대기였고 CPU 샘플은 적었다.
- 락 안 구간을 임시 계측으로 나눴다. 주문당 22.5ms 중 접수 트랜잭션 10.5ms, 정산 트랜잭션 10.4ms로 90% 이상이 DB 트랜잭션 두 번이었다. 매칭 자체는 0.1ms 미만이었다.
- `performance_schema`로 보면 주문 하나에 SQL 약 20개가 나가고, 그중 COMMIT 두 번이 평균 2.4ms씩으로 가장 컸다.

**해결.** 트랜잭션 경계와 동작은 그대로 두고 MySQL 드라이버 설정만 바꿨다.
- `useLocalSessionState`: 트랜잭션마다 나가던 `SET autocommit` 등 왕복 제거
- `rewriteBatchedStatements`: 주문당 약 5행인 원장 분개를 다중 행 INSERT 하나로
- 서버 측 준비문 캐시

**결과.** 같은 환경(4 vCPU 컨테이너 하나에 클라이언트·서버·MySQL, CPU 포화라 절대값은 하한)에서 나란히 비교했다.

| 50명, 3구단 | 처리량 | p99 | 락 안 시간 |
| --- | --- | --- | --- |
| 드라이버 기본값 | 94~113 주문/초 | 770~1,103ms | 22.5ms |
| 설정 후 | 132~139 주문/초 | 647~654ms | 18.5ms |

처리량이 약 25% 늘었고, 모든 실행에서 오류 0건, 대사 일치였다. 더 큰 개선(주문당 트랜잭션 하나로 합치기, 구단별 묶음 커밋)은 실패 처리 설계를 바꿔야 해서 측정 근거만 문서에 남겼다.

**배운 점.** 추측 대신 구간별로 재고 나니 "매칭 엔진 최적화"가 아니라 "커밋 횟수"가 문제였다. 정합성 확인을 부하 테스트의 통과 조건에 넣어, 빨라졌지만 틀린 결과를 성능 개선으로 착각하지 않게 했다.

## 8. 기준가가 바뀌는 순간 옛 제한폭으로 검증한 주문

- 구분: 버그 / 주제: 동시성, 경쟁 조건
- 관련: [#21](https://github.com/JiwonXD/TeamTrading/pull/21), [ADR 0018](adr/0018-daily-base-price.md)

**문제.** 가격제한폭(±30%)의 기준가가 구단별 고정값이라, 가격이 움직여도 제한폭이 출시 때 값에 머물렀다. 인기 구단은 상한가에 막혀 가격을 찾지 못했다. 기준가를 매일 전일 종가로 바꾸기로 하자 두 가지 정합성 문제가 드러났다.

**원인.**
- 주문 가격 검증이 종목 락 **밖**에 있었다. 기준가가 바뀌는 순간 옛 제한폭으로 검증을 통과한 주문이 새 기준가 아래에서 체결될 수 있었다.
- 팬차트 주문은 KRX와 달리 취소할 때까지 유효하다. 어제 낸 지정가가 새 제한폭 밖에 남아 있으면 그 가격에 체결돼 제한폭이 깨진다.

**해결.**
- 주문 검증을 종목 락 안으로 옮겨, 한 주문이 처음부터 끝까지 한 기준가만 보게 했다.
- 일 마감 뒤 `TradingService.startNewDay`가 종목 락 안에서 기준가를 바꾸고, 새 제한폭 밖으로 나간 대기 주문만 취소해 묶인 포인트·주식을 돌려준다. 취소는 사용자 취소와 같은 경로라 원장에 해제 전표가 남는다.
- 모든 대기 주문을 매일 취소하는 방안(KRX 방식)은 24시간 시장에서 자정마다 유동성이 끊겨 택하지 않았다.

**결과.** 23,900에 체결 후 일 마감하면 제한폭이 16,730~31,050으로 바뀌고, 13,000 매수는 취소·환불, 20,000 매수는 남으며 대사가 맞는다. 재기동해도 바뀐 기준가가 유지된다.

**배운 점.** 검증과 실행 사이에 상태가 바뀔 수 있으면 둘은 같은 락 안에 있어야 한다(TOCTOU). 기능 하나(기준가 갱신)를 더하면서 기존 코드의 경쟁 조건이 드러났다.

## 9. 지급받은 주식 때문에 수익률이 1,800%로 나옴

- 구분: 버그 / 주제: 계산 정합성
- 관련: [#7](https://github.com/JiwonXD/TeamTrading/pull/7), [#8](https://github.com/JiwonXD/TeamTrading/pull/8), [#11](https://github.com/JiwonXD/TeamTrading/pull/11)

**문제.** 초기 주식을 지급받은 계정의 수익률이 1,800%로 나왔다.

**원인.** 수익률 기준이 시작 포인트뿐이라, 무상으로 받은 주식의 평가액이 전부 투자 수익으로 잡혔다.

**해결.**
- 기준(`initial_value`)을 시작 포인트 + 지급 주식 평가액으로 바꿨다(#7).
- 이후 가입·광고·게시글 보상도 기준에 더해 수익률에 섞이지 않게 했다. 배당은 투자 수익이라 더하지 않는다(#8, #10).
- 리더보드는 외부 유입을 빼는 일 단위 시간가중수익률(TWR)로 계산한다(#11).

**결과.** 보상은 수익률에 잡히지 않고 배당은 잡히는 것을 테스트로 확인한다.

**배운 점.** 수익률은 "무엇이 투자 성과이고 무엇이 외부 유입인가"를 먼저 정의해야 계산할 수 있다. 포인트가 생기는 경로가 늘 때마다 이 분류를 함께 정했다.

## 10. 연결 전·끊긴 뒤 화면이 가짜 자산 값을 보여줌

- 구분: 버그 / 주제: 실시간 데이터
- 관련: [#19](https://github.com/JiwonXD/TeamTrading/pull/19), [ADR 0016](adr/0016-pwa-and-stale-data.md)

**문제.** PWA 작업 중, 서버 모드 화면이 서버 값을 받기 전이나 연결이 끊긴 뒤에 기본값(자산 100만P, 구단 기준가)을 실제 값처럼 보여주는 것을 발견했다. 첫 연결에 실패하면 다시 시도하지도 않았다.

**원인.** 화면 상태가 "서버에서 받은 값"과 "아직 모르는 값"을 구별하지 않고, 시뮬레이션 모드의 초기값으로 채워져 있었다.

**해결.**
- 연결 상태(`connecting`, `unreachable`, `live`, `stale`)를 두고, 서버 값을 한 번도 받지 못했으면 기본값 대신 연결 상태만 보여준 뒤 3초마다 다시 시도한다.
- 갱신이 실패하면 "HH:MM:SS 기준 값"이라고 알리고, 오프라인도 알린다. 401이면 로그인부터 다시 한다.

**결과.** API를 막는 E2E로 연결 불가 시 기본 자산 카드가 보이지 않음, 재연결, 끊김 표시와 해제를 확인한다.

**배운 점.** 금융 화면에서 오래된 값이나 가짜 값을 아무 표시 없이 보여주는 것은 틀린 값을 보여주는 것과 같다. "모른다"와 "언제 기준"을 표시하는 것도 데이터 정합성의 일부다.

## 11. 실시간 시세 스냅숏과 업데이트 사이의 틈

- 구분: 설계 / 주제: 실시간 데이터
- 관련: [#5](https://github.com/JiwonXD/TeamTrading/pull/5), [#7](https://github.com/JiwonXD/TeamTrading/pull/7), [ADR 0006](adr/0006-market-feed-seq.md)

**문제.** 클라이언트는 접속 때 호가 스냅숏을 받고 이후 업데이트를 이어 붙인다. 스냅숏과 첫 업데이트 사이에 업데이트가 빠지거나 순서가 바뀌면 화면의 호가가 틀린 채로 남는다. 느린 클라이언트 하나가 매칭 스레드를 붙잡을 위험도 있었다.

**해결.**
- 구단마다 1씩 늘어나는 `seq`와 서버 기동마다 바뀌는 `epoch`를 붙인다.
- WebSocket 구독 등록과 스냅숏 전송을 종목 락 안에서 함께 해 틈을 없앴다.
- 차분 대신 10단계 호가를 통째로 보내, 하나가 빠져도 다음 업데이트에서 바로 맞춰진다.
- 화면은 seq가 건너뛰거나 epoch가 바뀌면 이어 붙이지 않고 다시 접속해 스냅숏부터 받는다.
- 매칭 스레드는 세션별 큐(256건)에 넣기만 하고 전송은 세션마다 둔 가상 스레드가 한다. 큐가 넘친 세션은 끊는다.

**결과.** 실제 서버에 접속해 snapshot → update(seq+1, seq+2) 순서를 확인했다. 느린 세션을 끊은 횟수는 지표로 본다(#15).

**배운 점.** 실시간 데이터의 정합성은 "빨리 보내기"보다 "틀렸을 때 클라이언트가 스스로 알아채고 복구할 수 있게" 만드는 쪽이 핵심이었다.

## 12. 동시 요청으로 한도·유일성 규칙을 넘는 경우

- 구분: 설계 / 주제: 동시성
- 관련: [#8](https://github.com/JiwonXD/TeamTrading/pull/8), [#9](https://github.com/JiwonXD/TeamTrading/pull/9), [#12](https://github.com/JiwonXD/TeamTrading/pull/12), [#20](https://github.com/JiwonXD/TeamTrading/pull/20), [#23](https://github.com/JiwonXD/TeamTrading/pull/23), [#26](https://github.com/JiwonXD/TeamTrading/pull/26)

**문제.** "하루 N회", "계정당 1개", "한 번만 지급" 같은 규칙은 "세고 → 확인하고 → 쓰기"로 구현하면 동시 요청이 같은 순간에 확인을 통과해 규칙을 넘는다.

**해결.** 기능마다 DB가 최종 판정을 하도록 했다.
- 포인트 일일 한도: 계정 행을 `FOR UPDATE`로 잠근 뒤 횟수를 센다. 발행마다 `(source, source_ref)` 멱등키를 둔다(#8).
- 첫 소셜 로그인: 계정 생성·가입 보상·로그인 연결을 한 트랜잭션으로 묶고 `(provider, subject)` 유일 제약을 둔다(#9).
- 공모 청약: 공모 행 잠금 + 계정당 1건 기본키. 배정은 종목 락 → 공모 행 → 계정 행(id 순서)으로 체결 정산과 잠금 순서를 맞췄다(#12).
- 광고 보상 콜백, 성적 수당 지급: 행 잠금 + 상태 확인 + 멱등키(#20, #23).
- 닉네임: 변경 주기는 조건부 UPDATE, 중복은 고유 인덱스로 판정한다(#26).

**결과.**

| 시나리오 | 결과 |
| --- | --- |
| 포인트 동시 발행 40건 | 한도만큼만 지급 |
| 동시 첫 로그인 16건 | 계정 1개, 가입 보상 1건 |
| 40계정 × 중복 동시 청약 | 계정당 1건 |
| 같은 광고 세션 콜백 8건 동시 | 1회 지급, 대사 일치 |
| 성적 수당 동시 지급 요청 6건 | 1회 지급 |
| 경기 배당 동시 지급 8건 | 1회 지급 |

**배운 점.** 애플리케이션 코드의 확인은 동시성 앞에서 믿을 수 없다. 마지막 방어선은 DB 제약과 행 잠금에 두고, 여러 행을 잠글 때는 순서를 전 기능에서 통일해야 교착이 없다.

## 13. 배당 기준 시점 보유를 어떻게 정할 것인가

- 구분: 설계 / 주제: 정합성
- 관련: [#10](https://github.com/JiwonXD/TeamTrading/pull/10), [#28](https://github.com/JiwonXD/TeamTrading/pull/28), [ADR 0010](adr/0010-match-dividends.md), [ADR 0024](adr/0024-match-feed.md)

**문제.** 경기 시작 시각에 주식을 가진 사람에게 배당을 준다. 결과를 보고 산 주식이 배당을 받으면 안 된다.

**고민.**
- 시작 시각에 보유 스냅숏을 뜨는 방식은 그 시각에 스케줄러가 못 돌면(서버 중단) 기준이 틀어진다.
- 경기 데이터 제공처가 경기 중에 시작 시각을 늦춰 보내면, 그걸 받는 순간 경기를 보며 산 주식이 배당 대상에 들어간다.

**해결.**
- 스냅숏 대신 원장 전표를 기준 시각까지 더해 보유를 되짚는다(매도 주문에 묶인 몫 포함). 언제 다시 계산해도 같은 답이다.
- 결과 수신 후 6시간 확정 대기 뒤 지급하고, 대기 중 정정은 대기를 다시 시작한다. 지급 뒤 정정은 자동 회수하지 않고 REVIEW로 표시한다.
- 외부 데이터 연동(#28)에서는 시각 앞당기기는 늘 받고, 늦추기는 제공처가 시작 전(NS)·연기라고 할 때만 받는다.

**결과.** 시작 시각 보유자만 지급, 시작 뒤 매수 제외, 연기 시 기준 이동, 동시 지급 8건 → 1회를 테스트로 확인한다. demo 서버에서 가상 경기 3건을 지급(보유자 20명씩)하고 원장 발행 총량 = 발행 기록 합을 확인했다.

**배운 점.** 원장을 "시점별로 다시 계산할 수 있는 장부"로 쓰면 스냅숏 작업 없이도 과거 시점 정합성을 보장할 수 있다. 외부 데이터는 어떤 변경이 사용자에게 부당한 이득을 주는지부터 따져 받아야 한다.

## 14. 예상 체결가와 실제 시초가가 어긋날 수 있는 구조

- 구분: 설계 / 주제: 정합성
- 관련: [#13](https://github.com/JiwonXD/TeamTrading/pull/13), [#25](https://github.com/JiwonXD/TeamTrading/pull/25)

**문제.** 상장 동시호가 중 예상 체결가를 보여주기로 했다. 표시용 계산과 실제 체결 계산을 따로 구현하면 두 값이 어긋날 수 있고, 사용자는 화면을 보고 주문했는데 다른 가격에 체결된다.

**해결.** `OrderBook.indicative`가 호가창을 바꾸지 않고 단일가 가격·수량을 계산하고, 실제 체결(`uncross`)도 같은 함수를 쓰게 했다. 규칙은 체결량 최대 → 잔량 최소 → 기준가 근접이다.

**결과.** 동시호가 중 예상 체결가(19,000, 6주)가 상장 시각의 실제 체결과 같고, 계산해도 호가창 상태가 그대로인 것을 테스트로 확인한다.

**배운 점.** 같은 규칙을 두 곳에 구현하지 않는 것이 어긋남을 막는 가장 확실한 방법이다.

## 15. VI 상태가 메모리에만 있어 재시작하면 사라짐

- 구분: 설계 / 주제: 장애 복구
- 관련: [#27](https://github.com/JiwonXD/TeamTrading/pull/27), [ADR 0023](adr/0023-volatility-interruption.md)

**문제.** 변동성 완화장치(VI)가 발동하면 2분간 단일가 매매로 주문을 모은다. 이때는 호가가 교차한 채 쌓인다. VI 끝 시각은 메모리에만 있어서, 그 사이 재시작하면 교차한 호가창을 연속 매매로 복구하게 된다.

**해결.** 재시작 때 DB의 대기 주문이 교차해 있으면 VI 중이었던 것으로 보고 2분을 다시 시작한다. 별도 상태 테이블 없이 기존 데이터에서 상태를 판단한다. 또 VI 단일가 체결은 VI 직전 체결가와 비교해 가격 괴리를 기록해, 단일가 매매로 몰아주기 탐지를 피해 가지 못하게 했다.

**결과.** 재시작 중 VI 재개를 포함한 `VolatilityInterruptionTest` 5개, 전체 141개 테스트 통과. VI 규칙에 걸리던 기존 테스트는 VI 단일가 매매를 거치도록 고쳤다. MySQL 부하 테스트(주문 1,343건) 5xx 0건.

**배운 점.** 새 상태를 추가할 때마다 "재시작하면 이 상태는 어디서 복구되는가"를 먼저 물어야 한다.

## 16. CI의 E2E 테스트가 절반 확률로 실패

- 구분: 버그 / 주제: 테스트 안정성
- 관련: [#7](https://github.com/JiwonXD/TeamTrading/pull/7)(cd4c27e, e3025ce), [#26](https://github.com/JiwonXD/TeamTrading/pull/26) 전후(ae51eae)

**문제.** 주문·실시간 시세 E2E 테스트가 CI에서 약 절반 확률로 실패했다.

**원인.**
- demo 서버의 시뮬레이션 계정 주문이 무작위라, 기동 직후 테스트가 고정해 둔 구단에 매도 호가가 없는 경우가 있었다.
- 실시간 피드 테스트는 데모 체결이 제한 시간 안에 일어나기를 기다렸는데, 그게 보장되지 않았다.

**해결.**
- 실패 원인을 보기 위해 먼저 E2E 실패 시 서버 로그, 호가창, 페이지 스냅숏을 남기게 했다.
- 고정 구단 대신 매도 호가가 있는 구단을 고르게 했고, 이후 판매 호가가 여러 단계 있는 구단을 고르게 강화했다.
- 실시간 피드 테스트는 두 번째 로그인 사용자가 최우선 매도호가에 직접 사서, 관찰자가 그 체결을 WebSocket으로 받는지 확인하는 결정적 테스트로 바꿨다.
- Playwright가 리포트를 쓸 때 Vite가 페이지를 다시 읽던 문제도 함께 막았다.

**배운 점.** 무작위 데이터에 기대는 테스트는 테스트가 아니다. 실패를 고치기 전에 실패를 관찰할 수 있게 만드는 것이 먼저였다.

## 20. 집 PC(Windows)에서 배포 묶음이 80번 포트를 못 열고 멈춤

- 구분: 버그 / 주제: 배포
- 관련: [#33](https://github.com/JiwonXD/TeamTrading/pull/33), [#35](https://github.com/JiwonXD/TeamTrading/pull/35)

**문제.** 베타 서버로 쓸 Windows PC에서 `docker compose --profile quick-tunnel up -d --build`를 실행했다. 이미지 빌드와 MySQL·서버 기동까지는 됐는데 nginx 컨테이너가 `listen tcp 0.0.0.0:80: bind: An attempt was made to access a socket in a way forbidden by its access permissions`로 뜨지 않았다. CI(ubuntu)와 개발 환경에서는 한 번도 나지 않던 오류다.

**원인.** Windows는 80번을 다른 프로그램(IIS 등 http.sys를 쓰는 서비스)에 주었거나, Hyper-V·WSL이 예약한 포트 범위에 넣어 둘 수 있다. 그러면 Docker Desktop이 그 포트를 잡지 못한다. 묶음은 `HTTP_PORT` 기본값 80으로 nginx를 PC에 열고 있었다.

**해결.** 이 구성에서 PC의 80번은 필요 없다. Cloudflare Tunnel은 컨테이너 네트워크 안에서 `web:80`으로 붙고, 바깥 HTTPS는 Cloudflare가 받는다. 그래서 `.env`의 `HTTP_PORT=8088`로 PC 쪽 포트만 바꿨다. 코드의 기본값(80)은 그대로 두었다. 클라우드 VM이나 ALB 앞에서는 80이 맞기 때문이다. 대신 배포 문서에 이 오류 문구와 조치를 적었다.

**결과.** 다시 띄운 뒤 6개 컨테이너가 모두 올라왔고(mysql·backend·backup healthy), 화면은 `0.0.0.0:8088->80`으로 열렸다.

**배운 점.** CI가 리눅스에서만 돌면 운영 PC의 OS 차이는 잡히지 않는다. 바깥 연결이 터널이면 호스트 포트는 로컬 확인용일 뿐이므로, 충돌이 나는 값은 설정으로 빼 두면 된다.

## 21. PC로 접속해도 휴대폰 화면(480px 한 줄)만 보임

- 구분: 설계 / 주제: 화면, 반응형
- 관련: [#43](https://github.com/JiwonXD/TeamTrading/pull/43), [PC 화면 분석](desktop-ui-analysis.md)

**문제.** 베타를 연 뒤 PC 브라우저로 접속하면 1920px 모니터 가운데에 폭 480px짜리 휴대폰 화면이 떠 있었다. 아래 탭바, 호가를 누르면 아래에서 올라오는 주문 시트까지 모바일 그대로라 차트·호가·주문을 한 번에 볼 수 없었다. HTS와 비슷한 경험이 목표인데 PC에서 가장 거리가 멀었다.

**원인.** 모바일(최종 목표 MTS)부터 만들면서 `.app { max-width: 480px }` 한 줄 레이아웃만 있었고, 넓은 화면용 배치는 설계에 없었다. CSS 미디어 쿼리만으로 바꾸기도 어려웠다. 구단 화면은 "탭으로 호가/체결/토론 중 하나만 보이기 + 주문은 시트로 띄우기"라는 화면 구조 자체가 휴대폰용이라, 넓은 화면에서는 컴포넌트 배치가 달라야 했다.

**해결.** 사용자가 녹화한 토스증권 웹 영상(102초, 1920×1080)을 1초 간격 103장과 전환 구간 5fps로 잘라 배치와 마우스 동작을 정리했다([분석 문서](desktop-ui-analysis.md)). 그 결과로 `matchMedia('(min-width: 1024px)')`를 `useSyncExternalStore`로 구독하는 `useDesktop()`을 두고, 1024px 이상이면 PC 셸(위 메뉴 · 본문 · 오른쪽 구단 목록 · 아래 시세 띠)을 그리게 했다. 홈과 구단 화면은 PC 전용 배치(시세 표 + 미리보기, 차트·호가·주문 동시 배치)를 새로 만들고, 내 투자·랭킹·시장감시는 기존 컴포넌트를 그대로 넣어 카드를 두 단으로 흘렸다. 주문 검증·체결 로직은 기존 store 함수를 같이 써서 화면만 둘이고 동작은 하나다. 모바일 화면은 한 줄도 바꾸지 않았다(구단 화면의 체결·토론 컴포넌트를 PC에서 쓰도록 export만 추가).

**결과.** 1024px 미만은 기존 모바일 화면 그대로(390px 스크린샷 비교로 확인), 1440px·1600px에서는 차트·호가 20단계·주문창이 한 화면에 보인다. 호가를 누르면 주문창 가격과 구매/판매 방향이 바로 채워지고, 차트에서 오른쪽 클릭하면 그 가격(호가단위·가격제한폭에 맞춤)으로 주문을 채운다. 접근성 검사(axe) 위반 0건(라이트·다크, 화면 5개 + 검색창). PC 폭 E2E 3건을 `desktop` 프로젝트로 추가했다.

**배운 점.** 반응형은 CSS만의 문제가 아니라 화면 구조의 문제일 때가 있다. 넓은 화면에서 "동시에 보여줄 것"이 달라지면 컴포넌트 배치를 따로 두고, 데이터와 주문 로직만 공유하는 편이 깔끔하다.

## 22. PC 주문창의 가격·수량 입력칸이 패널 밖으로 넘침

- 구분: 버그 / 주제: 화면, CSS
- 관련: [#43](https://github.com/JiwonXD/TeamTrading/pull/43)

**문제.** 첫 PC 구단 화면 스크린샷에서 주문창의 가격·수량 입력칸이 패널 오른쪽 밖으로 삐져나가 −/+ 버튼이 안 보였고, 입력한 가격 글자도 잘려 보이지 않았다.

**원인.** 줄마다 `grid-template-columns: 72px 1fr`로 이름표와 입력칸을 놓았다. `1fr`은 `minmax(auto, 1fr)`이라 열이 내용의 최소 폭보다 좁아지지 않는다. 그런데 `<input>`은 `size` 기본값(약 20글자) 때문에 고유 폭이 150px가 넘어서, 입력칸 + 단위 + 버튼 두 개의 최소 폭이 패널 안쪽 폭(330px − 여백)을 넘었다. 입력에 `flex: 1; min-width: 0`을 줬지만 그건 flex 안쪽 문제만 풀고, 바깥 grid 칸의 최소 폭은 그대로였다.

**해결.** grid 칸 자식에 `min-width: 0`, 입력에 `width: 100%`를 줘서 grid 칸이 내용 최소 폭이 아니라 남은 공간에 맞춰지게 했다.

**결과.** 1280·1440·1600px 모두 입력칸과 −/+ 버튼이 패널 안에 들어오고, 가격은 `32,200`처럼 쉼표 형식으로 보인다.

**배운 점.** grid·flex의 `1fr`/`flex: 1`은 "남는 만큼"이 아니라 "최소 내용 폭 이상에서 남는 만큼"이다. 입력·긴 숫자가 들어가는 칸에는 `min-width: 0`을 기본으로 둔다.

## 23. 1280px 노트북에서 차트·호가·주문 3열이 찌그러짐

- 구분: 버그 / 주제: 화면, 반응형
- 관련: [#43](https://github.com/JiwonXD/TeamTrading/pull/43)

**문제.** 1600px에서는 괜찮던 구단 화면이 1280px 창에서는 차트 열이 200px 남짓으로 줄어 기간 버튼이 세로로 꺾이고 차트가 막대처럼 보였다. 1279px까지만 적용하는 미디어 쿼리를 걸어 두었는데 정확히 1280px에서는 빠져 있었고, 오른쪽 구단 목록(320px)을 접으면 본문이 넓어지는데도 화면 폭 기준이라 배치가 그대로였다.

**원인.** 열 개수를 정하는 건 화면(viewport) 폭이 아니라 본문 폭인데, 본문 폭은 화면 폭 − 구단 목록 폭(접힘 52px / 펼침 280~320px)이라 화면 폭만 보는 미디어 쿼리로는 맞출 수 없다.

**해결.** 본문(`.desk-main`)에 `container-type: inline-size`를 주고 컨테이너 쿼리로 바꿨다. 본문이 1180px 이하면 차트를 위 전체 폭에, 호가와 주문을 그 아래 두 열로 놓는다. 홈도 같은 기준으로 미리보기 패널을 숨긴다.

**결과.** 1280px(구단 목록 펼침)에서는 차트가 본문 전체 폭(약 910px)으로, 1600px에서는 3열로, 구단 목록을 접으면 그 자리에서 3열로 바뀐다.

**배운 점.** 사이드바가 열리고 닫히는 레이아웃에서는 미디어 쿼리보다 컨테이너 쿼리가 맞다.

## 24. 다크 모드에서 빨강·파랑 바탕 흰 글자 대비 부족(2.92:1)

- 구분: 버그 / 주제: 접근성
- 관련: [#43](https://github.com/JiwonXD/TeamTrading/pull/43)

**문제.** PC 화면을 axe로 검사하니 라이트 모드는 통과했지만 다크 모드 구단 화면에서 `color-contrast` 위반이 나왔다. 차트 오른쪽 현재가 표(흰 글자 / 파랑 #4c97ff, 2.92:1)와 주문창 구매 탭(흰 글자 / 빨강 #ff5a66, 3.04:1)이 기준 4.5:1에 못 미쳤다.

**원인.** 다크 모드에서는 어두운 바탕 위에서 잘 보이도록 빨강·파랑을 밝게 바꾼다. 그 색을 다시 "바탕"으로 쓰면 흰 글자와의 대비가 떨어진다. 라이트 모드 기준으로 `color: #fff`를 박아 둔 게 원인이었다.

**해결.** PC 셸에 `--on-accent` 토큰(라이트 #fff, 다크 #101013)을 두고 빨강·파랑 바탕 위 글자는 모두 이 토큰을 쓰게 했다.

**결과.** axe 위반 0건(라이트·다크 × 홈·구단·내 투자·랭킹·시장감시·검색창).

**배운 점.** 색 토큰은 "글자색"과 "바탕색"을 따로 정의해야 한다. 같은 빨강이 글자일 때와 바탕일 때 짝이 되는 색이 다르다.

## 25. 이상거래 탐지 기록(의심 계정 닉네임)이 모든 유저에게 공개돼 있었음

- 구분: 설계 / 주제: 보안, 감시
- 관련: [#45](https://github.com/JiwonXD/TeamTrading/pull/45), [ADR 0026](adr/0026-surveillance-admin-only.md)

**문제.** 베타 서버를 열고 나서 "시장감시 탭은 운영자 계정에만 보이나?"라는 질문을 받고 확인해 보니, 일반 계정에도 아래 탭(PC는 위 메뉴)에 시장감시가 보였다. `GET /api/surveillance/alerts`도 로그인 없이 부를 수 있어서 반복 상대 체결·가격 괴리로 기록된 양쪽 계정의 닉네임을 누구나 볼 수 있었다.

**원인.** 처음에는 브라우저 안 시뮬레이션 미리보기로 FDS 동작을 보여주려고 "운영자 화면 예시" 탭을 모든 사람에게 보였다. 서버로 옮길 때(ADR 0009) 계정 id는 빼고 닉네임만 내보내면 공개해도 된다고 보고 그대로 열어 두었다. 미리보기의 시연용 결정이 실서비스 권한 설계로 이어진 것이다.

**해결.** 탐지 기록 API를 `/api/surveillance/**`로 묶어 운영자(`ROLE_ADMIN`)만 부를 수 있게 했다. `GET /api/accounts/me`에 `admin`을 더해 화면은 운영자에게만 시장감시 메뉴와 `#watch` 주소를 보이고, 일반 계정은 3초 갱신 때 탐지 기록을 요청하지 않는다. 닉네임만 가려서 공개하는 안도 봤지만, 어떤 거래가 기록되는지(횟수·간격·가격 차이)가 실시간으로 보이면 포인트를 옮기려는 사람이 기준을 피해 갈 수 있어 버렸다.

**결과.** 로그인 안 함 401, 일반 계정 403, 운영자 200(AuthTest). `admin` 값은 일반 false, 운영자 true. 일반 계정 화면의 탭은 홈·내 투자·랭킹 3개만 남는다.

**배운 점.** 시연용으로 연 데이터는 실서비스로 넘어갈 때 "누가 봐도 되는가"를 다시 따져야 한다. 메뉴 숨김은 권한이 아니므로 API 권한부터 막는다.

## 26. 리그 카테고리를 어디에 두고, 고른 리그를 어떻게 보여줄까

- 구분: 설계 / 주제: 정보 구조, 내비게이션, 비동기 응답 순서
- 관련: [#46](https://github.com/JiwonXD/TeamTrading/pull/46)

**문제.** KBO·K리그·LCK를 토스증권의 국내·해외처럼 나눠 보는 화면이 필요했다. 처음 안은 두 가지였다. (1) 리그를 위 메뉴(홈·내 투자·랭킹 옆)에 넣는다. (2) 리그를 고르면 왼쪽 위 팬차트 로고 자리에 리그 이름을 띄운다.

**원인(검토).** 위 메뉴는 "어디로 갈지"(홈, 내 투자, 랭킹)를 고르는 곳이고 리그는 "무엇을 볼지"를 좁히는 필터라 층위가 다르다. 메뉴에 섞으면 리그가 늘 때마다(V리그, KBL…) 메뉴가 길어지고, 모바일 아래 탭(4칸)에는 들어가지도 않는다. 로고 자리는 거의 모든 서비스에서 "누르면 홈"과 브랜드 인지를 맡는 고정 자리다. 리그 이름으로 바꾸면 홈으로 돌아가는 길이 사라지고, '팬차트' 이름이 음원 차트로 오해받을 수 있다는 기존 우려도 커진다.

**해결.** 로고와 위 메뉴는 그대로 두고, 홈 맨 위에 굵은 글자 탭(전체·KBO·K리그·LCK)을 두었다. 리그를 고르면 주소가 `#league-kbo`처럼 바뀌어 뒤로 가기·공유가 되고, 위 메뉴는 계속 '홈'에 불이 켜진다. 고른 리그 이름은 탭과 "KBO 구단 시세" 제목으로 드러난다. 리그 화면은 스포츠 포털(네이버 스포츠, SOOP e스포츠)의 일정 화면처럼 위에 주간 달력과 그날 경기를, 아래에 그 리그 구단 시세를 둔다. 경기 속 구단을 누르면 바로 호가·주문 화면으로 간다. 주문을 팝업으로 바로 받는 안은 호가를 보지 않고 주문하게 되어 버렸다. 서버에는 `GET /api/matches/schedule?league&from&to`(31일 이내)를 추가했다. 기간은 화면이 사용자 시간대의 자정을 시각으로 바꿔 보내므로 서버가 시간대를 알 필요가 없다.

달력에서 주를 빠르게 넘기면 앞 주 요청이 늦게 도착해 다른 주 경기가 섞여 보일 수 있다. 응답을 "리그:주 시작 시각" 키와 함께 저장하고, 지금 보는 키와 같을 때만 그리도록 했다.

**결과.** 서버 연동 E2E 18개 통과(모바일·PC 리그 화면, axe 위반 0건 포함). 일정 API 테스트 2개(리그·기간 필터와 정렬, 뒤집힌 기간·31일 초과·없는 리그 400).

**배운 점.** 사용자가 원하는 것(지금 어느 리그를 보는지 분명히)과 제안한 방법(로고 자리 교체)을 나눠서 보면, 관례를 지키면서도 원하는 것을 줄 수 있다.

## 27. 리그가 여섯 개로 늘자 제공처 하나·키 하나 구조가 버티지 못했다

- 구분: 설계 / 주제: 외부 연동, 장애 격리, 요청 한도
- 관련: [#48](https://github.com/JiwonXD/TeamTrading/pull/48), [ADR 0027](adr/0027-per-league-feed-providers.md)

**문제.** KBO·LCK·프리미어리그·라리가·세리에A·분데스리가의 일정·결과를 받아야 했다. 기존 수집(ADR 0024)은 API-Sports 키 하나(`MATCH_FEED_API_KEY`)로 KBO와 K리그만 받았다. 키를 넣으면 모든 리그가 켜지고 빼면 모두 꺼지는 구조였다.

**원인(검토).** 한 제공처로 여섯 리그를 덮을 수 없었다. LCK는 API-Sports에 없고, API-Sports 무료 요금제는 유럽 리그의 현재 시즌 제공 여부가 문서상 불분명했다("recent seasons"). 키가 하나면 한 리그 문제(만료, 요금제 변경)로 전 리그가 멈추고, 리그를 하나씩 붙여 확인할 수도 없다. 요청 한도도 처음엔 "제공처별로 센다"였는데, 무료 한도는 실제로 **계정(키)마다** 걸린다. 리그마다 따로 세면 같은 football-data 키를 쓰는 유럽 4개 리그가 한도의 4배를 쓸 수 있다.

**해결.** 리그마다 제공처·키·리그 번호를 따로 두고(`KBO_API_KEY`, `LCK_API_KEY`, `EPL_API_KEY` …), 키가 빈 리그만 쉬게 했다. 제공처는 `FeedProvider`(요청 모양 + 응답 해석) 하나만 더하면 붙고, 응답을 공통 `FeedGame`으로 옮긴 뒤의 배당 안전 규칙(늦추는 시각 변경 거절, 확정 대기, 정정 시 REVIEW)은 그대로 재사용한다. 유럽 4대 리그는 football-data.org, LCK는 PandaScore를 붙였다. 요청 한도는 "제공처 + 키" 단위로 센다. 제공처마다 다른 함정도 막았다. football-data의 날짜 조건은 UTC 날짜라 한국 시간 하루를 덮도록 전날부터 묻고, PandaScore의 플레이오프 대진 미정 경기(상대 없음)와 몰수 경기는 결과로 쓰지 않는다. 키가 로그에 찍히지 않도록 설정 객체의 문자열 표현에서 키를 뺐다. LoL Esports 비공식 API와 KBO 공식 사이트 수집은 약관·무단 변경 위험으로 버렸다.

**결과.** 수집 테스트 24개 통과(제공처별 요청 주소·인증 헤더, 상태 코드 해석, 대진 미정·몰수 건너뛰기, 같은 키 리그끼리 한도 공유, 키 없는 리그는 요청 0건). 백엔드 전체 테스트 통과. 실제 제공처 호출은 이 작업 환경에서 막혀 있어 키 발급 뒤 운영 절차(docs/operations.md)로 확인한다.

**배운 점.** 외부 API 한도는 "무엇을 부르느냐"가 아니라 "누구 이름으로 부르느냐"(계정·키)에 걸린다. 한도를 세는 단위를 제공처의 과금 단위와 맞춰야 한다.
