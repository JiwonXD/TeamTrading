# 0009. 소셜 로그인과 세션 쿠키로 계정을 구분한다

- 상태: 채택
- 날짜: 2026-11-02

## 배경

지금까지는 `X-Account-Id` 헤더로 계정을 구분했다. 계정 id를 아는 사람은 그 계정으로 주문할 수 있었고, `POST /api/accounts`로 누구나 계정을 무한히 만들어 가입 포인트를 받을 수 있었다. 여러 사람이 쓰는 서비스로 열려면 둘 다 막아야 한다.

## 결정

- 계정은 로그인으로만 생긴다. 카카오·네이버·구글 OAuth 2.0 로그인 후 제공자의 사용자 고유 id(`provider`, `subject`)를 `account_identities`에 계정과 연결한다. 개인정보(이메일, 이름)는 받지 않는다.
- 첫 로그인의 계정 생성, 가입 보상, 로그인 수단 연결은 한 트랜잭션이다. 같은 사용자의 첫 로그인이 동시에 와도 기본키 충돌로 한쪽이 롤백되어 계정과 가입 보상은 하나만 남는다.
- 세션에는 계정 id와 권한만 담은 `AccountAuthentication`을 저장한다. 제공자 토큰은 세션에 남기지 않는다. 로그인 시 세션 id를 바꿔 세션 고정 공격을 막는다.
- 쿠키 인증이므로 상태를 바꾸는 요청은 CSRF 토큰을 요구한다(Spring Security SPA 방식: `XSRF-TOKEN` 쿠키 → `X-XSRF-TOKEN` 헤더).
- 시세·호가·체결·랭킹·탐지 기록·실시간 시세는 로그인 없이 볼 수 있다. 계정 id가 보이는 대사 결과는 운영자(`teamtrading.auth.admins`)만 본다.
- `demo` 프로필은 키 없이 닉네임으로 로그인하는 개발용 경로를 연다. E2E와 시연 서버가 쓴다. 운영 설정에서는 꺼져 있다.

## 검토한 대안

- JWT를 브라우저 저장소에 보관: XSS 한 번에 토큰이 유출되고, 로그아웃·강제 만료가 어렵다. 같은 도메인의 웹 화면에는 HttpOnly 세션 쿠키가 단순하고 안전하다. 모바일 앱 단계에서 토큰 방식이 필요하면 그때 추가한다.
- 아이디·비밀번호 가입: 비밀번호 저장·재설정·유출 대응을 직접 해야 하고, 다계정 생성 비용이 소셜 로그인보다 낮다.

## 결과

- 다계정 농사는 소셜 계정 수만큼으로 제한되지만 완전히 막히지는 않는다. 이상거래 탐지(우회 이전 패턴)와 함께 쓴다.
- 서버를 여러 대로 늘리면 세션 저장소(Spring Session + DB 또는 Redis)가 필요하다.
- 닉네임은 처음에 `투자자1234` 형태로 자동으로 정해진다. 닉네임 변경은 이후 추가한다.
