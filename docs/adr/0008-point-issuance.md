# 0008. 포인트 발행은 경로별 기록과 일일 한도를 거친다

- 상태: 채택
- 날짜: 2026-11-02

## 배경

포인트는 가입, 광고 시청, 종목토론방 게시글, 이후 경기 배당으로 새로 생긴다. 현금성은 없지만 발행이 통제되지 않으면 모든 가격이 인플레이션으로 의미를 잃고, 다계정으로 보상을 모아 체결로 한 계정에 몰아주는 우회 이전이 쉬워진다. 원장(0005)은 발행처(SYSTEM ISSUED)에서 나간 총량은 알지만 어떤 경로로 얼마가 나갔는지는 모른다.

## 결정

- 포인트를 새로 만드는 코드는 `PointIssuer` 하나다. 발행 기록(`point_grants`), 원장 전표(`ISSUE`), 잔고 변경을 한 트랜잭션에서 남긴다.
- `(source, source_ref)`를 멱등키로 둔다. 같은 광고 콜백 거래 id나 같은 게시글로는 한 번만 지급하고, 다시 부르면 처음 기록을 돌려준다. 다른 계정이 같은 키를 쓰면 충돌로 거절한다.
- 경로마다 1회 지급액과 하루(KST 자정 기준) 한도를 둔다. 계정 행을 `FOR UPDATE`로 잠근 뒤 오늘 지급 횟수를 세므로 동시 요청도 한도를 넘지 못한다.
- 발행분은 수익률 기준(`initial_value`)에도 더한다. 활동 보상은 외부 유입이지 투자 수익이 아니다.
- 대사는 원장 발행처에서 나간 포인트와 발행 기록 합이 같은지도 확인하고, 경로별 합계를 보고한다.

| 경로 | 1회 지급 | 하루 한도 | 멱등키 |
|---|---|---|---|
| 가입 | 1,000,000 | 계정당 1회 | 계정 id |
| 광고 시청 | 1,000 | 10회 | 광고 네트워크 서버 콜백의 거래 id |
| 게시글 | 2,000 | 3회 | 게시글 id |

지급액은 시작값이며 운영 데이터를 보고 조정한다.

## 검토한 대안

- 원장 전표에 경로 칸 추가: 한도 계산과 멱등키 검사를 위해 결국 별도 인덱스가 필요하고, 원장은 경로와 무관한 이동 기록으로 두는 편이 단순하다.
- 애플리케이션 메모리의 카운터로 한도 관리: 서버가 여러 대가 되거나 재시작하면 틀린다.

## 결과

- 광고와 게시글 보상의 공개 API는 아직 없다. 광고는 서버 측 검증 콜백(M6), 게시글은 토론방 서버 저장(M4)과 함께 붙인다.
- 기존 가입 지급(`OPEN_ACCOUNT` 전표)은 마이그레이션에서 발행 기록으로 옮겨 적어 대사가 그대로 맞는다.
