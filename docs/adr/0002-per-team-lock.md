# 0002. 종목별 락 + 메모리 호가창

- 상태: 채택
- 날짜: 2026-10-28

## 배경

같은 구단의 주문은 들어온 순서대로 처리해야 가격·시간 우선이 지켜진다. 구단은 18개이고 서로 다른 구단의 주문은 독립적이다.

## 결정

구단마다 공정(fair) `ReentrantLock` 하나를 두고, 락 안에서 메모리 호가창으로 매칭한다. 다른 구단끼리는 동시에 처리한다.

## 검토한 대안

- LMAX Disruptor 같은 단일 스레드 이벤트 루프: 처리량은 높지만 지금 규모에서는 구조가 과하다.
- DB 행 잠금만으로 매칭: 매칭마다 호가를 DB에서 읽어야 해서 느리고 교착 위험이 크다.
- Redis 분산 락: 서버가 하나라 필요 없다.

## 결과

- 매칭 로직은 단일 스레드 코드처럼 단순하다.
- 서버를 여러 대로 늘리려면 구단별로 담당 서버를 나누는 구조가 필요하다.
- 락 안에서 하는 일(정산 트랜잭션, 시세 발행)이 길어지면 그 구단 전체가 느려지므로, 시세 전송은 락 밖 스레드로 넘긴다 (0006).
