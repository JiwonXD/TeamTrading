# 0019. 구단 목록은 DB에 두고, 새 구단은 첫 상장 공모를 거쳐서만 거래한다

- 상태: 채택
- 날짜: 2026-11-02

## 배경

구단 18개가 백엔드 코드와 프론트엔드 목업에 따로 박혀 있었다. 리그 구단을 더하거나 이름을 바꾸려면 두 곳을 고쳐 다시 배포해야 했다. 새 구단을 운영자 고정가 판매로 시작하는 것은 이미 기각했다(시스템 마켓메이커 금지, 0012). 따라서 새 구단의 주식은 공모 청약과 상장 동시호가(0012, 0013)로만 생겨야 한다.

## 결정

- **`teams` 테이블.** id, 이름, 짧은 이름, 리그, 색, 첫 기준가, 정렬 순서를 둔다. 출시 때 18개는 마이그레이션으로 넣는다. `TeamCatalog`는 기동할 때 읽고, 등록하면 목록을 통째로 바꿔 끼운다. 읽기는 잠금 없이 한다.
- **등록** `POST /api/admin/teams`(운영자).
  - id는 영문 소문자·숫자·하이픈 2~20자이고, 같은 id는 409로 거절한다.
  - 첫 기준가는 호가 단위에 맞아야 한다.
  - 등록하면 거래 엔진이 종목을 바로 열지만 주문은 받지 않는다(`ipo_required`).
- **거래 시작은 첫 상장 공모로만.** 운영자가 공모를 등록하면 청약 → 배정 → 상장 동시호가 → 연속 매매 순서로 진행한다.
  - 공모가 취소되면 다시 공모할 때까지 거래를 막는다.
  - 기동할 때는 "등록했고, 주식이 없고, 진행 중인 첫 상장 공모가 없는" 구단을 다시 막는다. 이 상태는 DB에서 계산하므로 따로 저장하지 않는다.
- **화면.**
  - 서버 모드는 구단 목록(이름, 리그, 색)을 서버 시세 응답에서 받는다.
  - 상장 전 구단은 등락률 대신 "상장 전"으로 보여준다.
  - 화면 경로가 하이픈이 들어간 구단 id를 받는다.

## 검토한 대안

- **코드 목록 유지:** 리그를 넓힐 때마다 배포가 필요하고, 프론트와 백엔드 목록이 어긋날 수 있다.
- **등록하자마자 거래:** 주식이 아무에게도 없어 매수 주문만 쌓이고 포인트가 묶인다.
- **리그도 데이터로:** 리그마다 경기 데이터 연동과 배당 규칙이 필요하다. 리그는 지금처럼 코드(KBO, K리그, LCK)에 두고, 그 안의 구단만 데이터로 둔다.

## 결과

- 리그 확장은 운영 작업이 된다: 구단 등록 → 첫 상장 공모 등록. 사용 방법은 docs/operations.md에 있다.
- 사용자가 적을 때 구단을 늘리면 호가가 얇아진다. 구단은 사용자 수를 보고 늘린다.
