# 0040. 자동매매 봇 계정을 두고, 부하는 운영과 분리한 스택에서 잰다

- 상태: 채택
- 날짜: 2026-11-11

## 배경

2026-11-08에는 봇 계정을 기각했다. 봇끼리 체결은 가장매매와 같고, 봇이 호가를 계속 대면 사실상 시스템 마켓메이커라서다(0038 "검토한 대안", 트러블슈팅 43). 대신 운영자 매도 계단과 매일 할인을 넣었지만, 사려는 사람이 적은 콜드스타트는 그대로였다.

다시 검토하며 목적이 바뀌었다. 사이트를 사람 없는 채로 두기보다 가상의 사용자라도 돌려, 실제 트래픽에서 서버가 어디서 막히는지 겪어 보는 쪽이 낫다. 기준은 "사용자 1,000명"이다.

## 결정

- **봇은 일반 계정이다.** 비밀 값(`BOT_TOKEN`)을 아는 봇 실행기만 `/api/auth/bot-login`으로 이름만 대고 로그인하고, 처음이면 가입 포인트를 받는다. 운영자처럼 주식을 새로 만들지 않는다.
- **봇끼리의 체결도 허용한다.** 사용자 1,000명이 서로 주고받는 상황을 재현하는 게 목적이다. 대신 봇은 순위·리더보드에서 빼고, 봇끼리의 체결만 이상거래 탐지에서 뺀다. 봇과 사람의 체결은 그대로 검사한다.
- **봇은 화면과 같은 요청을 보낸다.** 3초 새로 고침 10건, 구단 시세 WebSocket, 가끔 주문. 주문만 보내는 부하 시험(`LoadTest`)과 달리 조회가 대부분인 실제 사용 패턴을 잰다.
- **한계는 분리한 스택에서 먼저 잰다.** 운영 백업을 복사한 측정 스택(`compose.load.yml`)에서 봇 1,000개로 한계와 병목을 찾고, 실서버에는 그 안의 수만큼만 상시로 띄운다.

## 결과

- 실서버 시세·차트·거래량에 봇 거래가 섞인다. 사람 사용자의 순위와 이상거래 탐지는 봇에 흐려지지 않는다.
- 봇 계정 표시는 계정 연결(`account_identities.provider = 'bot'`)로 하므로 새 컬럼이 없다. 서버는 기동 때와 봇 로그인 때 봇 계정을 메모리에 올린다.
- 처음 측정에서 병목 두 개를 찾아 고쳤다(트러블슈팅 47).

## 검토한 대안

- **봇끼리 체결하지 않는 호가 공급 봇만:** 가장매매 문제는 없지만, 사람이 적을 때 체결이 거의 생기지 않아 부하 경험이 되지 않는다.
- **실서버에서 바로 1,000개:** 집 PC 한 대가 몇 명을 버티는지 모르는 채 올리면 실사용자도 같이 느려진다.
- **봇 계정을 아이디·비밀번호로 가입:** 가입 IP 제한(1시간 10번) 때문에 1,000개를 만드는 데 100시간이 걸린다.
