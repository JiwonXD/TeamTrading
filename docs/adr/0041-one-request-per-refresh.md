# 0041. 화면 새로 고침은 요청 한 번으로 받는다

- 상태: 채택
- 날짜: 2026-11-12

## 배경

서버 모드 화면은 3초마다 조회 API 11개를 따로 부른다(시세, 순위, 경기, 청약, 내 계좌·주문·체결·배당·청약·광고, 보고 있는 구단 토론). 봇 300개로 서버 CPU를 샘플링하니 컨트롤러 안은 30%였고, 70%는 보안 필터 체인·지표·Tomcat처럼 요청 한 건마다 드는 공통 처리였다(트러블슈팅 49). 사용자 수가 늘면 요청 수가 11배로 늘고, 그 대부분이 같은 공통 처리다.

## 결정

- `GET /api/refresh`가 새로 고침 한 번에 필요한 값을 한 응답으로 준다. `mine=true`면 내 계정 값을, `posts=구단,…`이면 그 구단 토론(최근 30개, 한 번에 10개 구단까지)을 함께 준다.
- 값은 따로 있는 조회 API를 그대로 불러 묶는다. 따로 부르는 API는 다른 화면과 도구를 위해 그대로 둔다. 두 값이 같다는 것은 `RefreshApiTest`로 고정한다.
- 로그인 규칙은 전과 같다. `mine=true`인데 세션이 없으면 401이라, 화면은 전처럼 로그인 확인부터 다시 한다. 이상거래 기록은 운영자에게만 준다.

## 결과

- 같은 봇 수에서 서버 CPU가 42% 줄었다(봇 300개, 73% → 42%). 봇 1,000개도 오류 없이 받는다.
- 새로 고침의 응답 하나가 커졌다(구단 140개 시세 포함). 한 값이 실패하면 새로 고침 전체가 실패하는데, 전에도 `Promise.all`로 묶어 받아 같았다.
- 다음 한계는 새로 고침마다 도는 작은 쿼리 13개를 처리하는 MySQL이다.

## 검토한 대안

- **보안 필터 관측 끄기:** 단독으로는 효과가 있었지만, 요청을 묶은 뒤에는 차이가 없었다.
- **자주 안 바뀌는 값은 덜 자주 받기:** 배당·청약 결과가 늦게 보이는 동작 변경이다.
- **서버가 바뀐 값만 밀어 주기:** 효과는 가장 크지만 계좌가 바뀌는 모든 경로를 알림으로 만들어야 한다. 사용자가 더 늘면 다시 검토한다.
